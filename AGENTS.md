# AGENTS.md

High-signal guidance for coding agents (Claude Code, OpenCode, ...) in this repo. `CLAUDE.md` has the commands and rules you need first.

## Project in one line

Open Knowledge UI: German Flask RAG app + React SPA with SSE chat, user accounts with fixed roles (admin/editor/user), SQLAlchemy settings/chat/document tracking, Qdrant hybrid search (dense + sparse/BM25), knowledge of three kinds (local documents, foreign Qdrant, live read-only SQL databases), code execution (Pandas) and SQL access isolated in separate worker containers (`tool_worker/`), and OpenAI-compatible LLMs plus TEI/Infinity for embeddings/reranking.

## Entry points and run commands

```bash
# Install dependencies (uses uv)
uv sync

# Windows (no admin required; auto-downloads qdrant.exe)
start.bat
# Or directly
python run_windows.py              # with local Qdrant
python run_windows.py --no-qdrant  # if you run Qdrant separately

# Linux / Docker
alembic upgrade head
python run_linux.py
# needs TOOL_WORKER_TOKEN in .env (docker compose refuses to start without it)
docker compose up -d --build
# no NVIDIA GPU / ARM: docker compose -f docker-compose.yml -f docker-compose.cpu.yml up -d --build
# macOS: python run_mac.py (app native, helper services + workers in Docker)
```

- Windows default URL: `http://127.0.0.1:5000` (localhost only; no firewall prompt).
- Linux/Docker host port: `docker compose up` maps `8083:5000` (host:container) — the app is on `http://localhost:8083`, not 5000. 
- Linux manual (`python run_linux.py`, no Docker) binds `0.0.0.0:5000`.
- Default login: user `admin`, password `admin` (seeded once by `app/auth/users.py:ensure_admin_user` when the `users` table is empty; the password is the existing `APP_PASSWORD_HASH`, default `admin` / `ADMIN_PASSWORD` on a fresh DB, so installs keep their set password). Session cookie holds only `user_id` (`app/auth/auth.py:current_user` loads role/active state per request; deactivating a user ends their session). Roles are ordered `user` < `editor` < `admin`: `@require_role("editor")` guards knowledge/document/vector-DB/stats endpoints, `@require_role("admin")` guards settings, connections/models chat, own sessions, attachments, `GET /api/knowledge`, summaries and `GET /api/models` need only login. Chats are private per user (`sessions.user_id`; foreign IDs return 404, including `/chat/stop` and attachments). Login is throttled per username (5 failures / 5 min, in-memory). Non-admins get `/api/models` without prompt/params (`knowledge_locked` flag only). Not built yet: OIDC.
- Both `run_windows.py` and `run_linux.py` run `alembic upgrade head` automatically before starting the server.

## Database: Postgres (SQLite only for dev/tests) and Alembic baseline

- The initial migration (`alembic/versions/0001_initial_schema_and_admin_seed.py`) creates all tables and seeds an admin user (`admin` / `admin`).
- Migration `0002_single_user_conversion.py` drops the original `users` table (re-introduced in `0010`), moves the admin password hash into the `APP_PASSWORD_HASH` setting row, and removes all `user_id` FKs (single-user). `0003_embedding_model_prefix.py` rewrites `EMBEDDING_MODEL` to the HF-org-prefixed form fastembed needs.
- `app.db` may already exist, created by `DatabaseService` calling `Base.metadata.create_all()` in `app/__init__.py` (not by Alembic). On an existing `app.db`, `alembic upgrade head` fails with "table already exists" — run `alembic stamp head` to mark it as migrated without executing DDL, or delete `app.db` to start fresh.
- `run_windows.py` / `run_linux.py` run `alembic upgrade head` automatically before starting the server; on a fresh DB this creates the schema + admin seed.

## Releases and versioning

- Version source of truth: `pyproject.toml`. `scripts/release.py` (stdlib only, tested in `tests/test_release.py`) keeps `frontend/package.json`, `frontend/package-lock.json` and the project block in `uv.lock` in sync: `current`, `check [--tag vX.Y.Z]`, `bump patch|minor|major|X.Y.Z [--dry-run]`, `notes [--version X.Y.Z]`, `publish [--yes]`. `bump` requires a clean tree (untracked files count) on `master` (`--branch` overrides), moves `## [Unreleased]` in `CHANGELOG.md` to the new version (or generates it from Conventional Commits since the last `v*` tag), commits `chore(release): vX.Y.Z` and creates an annotated tag. With no `v*` tag yet, `bump 0.1.0` (same version) is the first release. `publish` only prints commands without `--yes`.
- `.github/workflows/ci.yml` (tests + frontend build on push to master / PRs) and `release.yml` (on tag `vX.Y.Z`: `release.py check --tag`, tests, build, then `gh release create` with the changelog section). The script never creates the GitHub release itself. All actions are pinned to full commit SHAs (a test enforces it; Dependabot keeps them current), checkouts use `persist-credentials: false`, and only the last `release` job has `contents: write` while `verify` (tests, build) runs read-only. Keep a non-empty changelog section per released version: the release workflow fails without one.
- `app/core/version.py` reads the version from `pyproject.toml` (fallback env `APP_VERSION`); exposed as `GET /api/version`, in `/health`, and in the sidebar/account dialog.
- Never tag, commit or push on your own initiative; the user decides when to release (current line is 0.2.x). Never add a `Co-Authored-By` trailer. Force-pushes are blocked by the sandbox: prepare a script and let the user run it.

## Frontend (React SPA)

- The UI is a React 19 + TypeScript SPA under `frontend/` (Vite + Tailwind v4 via `@tailwindcss/vite`, shadcn/ui components). It builds directly to `app/static/` (Vite `base: /static/`); Flask serves that directory and the 404 fallback handler in `app/api/pages.py:spa_fallback()` returns `index.html` for client-side routes (true catch-all; `/api/`, `/static/`, `/ws/` and non-GET are excluded). There are **no Jinja templates for the app shell anymore** — `frontend/index.html` is the only HTML entry point.
- Build: `cd frontend && npm install && npm run build` (runs `scripts/clean-static.mjs` first, then `tsc -b && vite build` → `app/static/`). Dev: `npm run dev` on :5173 with proxy to Flask on :5000; run the backend separately. The Vite proxy must only cover backend paths (`/api`, `/chat`, `/user`, `/logout`, `/health`, `/ws`) — client routes stay on the dev server.
- JSON API lives in `app/api/` (`/api/*`, one blueprint per area, see the package map below) and uses `auth_required_api`/`require_role` (`app/auth/auth.py`) which return `401` JSON instead of redirecting to `/login`. Outside `/api`: `/chat`, `/chat/stop`, `/history/<id>` (`app/api/chat.py`), `/`, `/login`, `/logout`, `/health` (`app/api/pages.py`) and `/ws/stt-stream` (`app/chat/stt_stream.py`). The legacy `/user/*` blueprint is gone; summary downloads are `/api/summaries/<f>/download-md|docx`.
- Design tokens (ChatGPT-like neutrals, dark mode via `<html class="dark">`) are defined in `frontend/src/index.css` under `@theme` (`--color-surface`, `--color-primary`, `--color-border-base` …) + shadcn semantic tokens bridged onto them. **Do not** add per-element `dark:` variants — extend the tokens instead. Theme bootstrap runs inline in `frontend/index.html` before first paint (FOUC avoidance); `src/lib/theme.ts` + `src/context/ThemeContext.tsx` handle runtime switching. The server injects `UI_THEME` into the index via `serve_spa()` (placeholder `__RAG_UI_THEME__`).
- The Docker build is multi-stage: a `node:22-slim` stage runs `npm ci && npm run build` and the resulting `app/static` is copied into the Python runtime image (there is no Tailwind standalone CLI / `tailwind.config.js` anymore). `.dockerignore` excludes `frontend/node_modules`, `frontend/dist`, and the generated `app/static/{index.html,assets,favicon.svg,pcm-worklet-processor.js}`.
- The PCM AudioWorklet for live STT lives at `frontend/public/pcm-worklet-processor.js` and is served as `/static/pcm-worklet-processor.js` (referenced in `src/hooks/useStt.ts`).

## Key architecture facts

- App factory: `app/__init__.py:create_app()`. Qdrant client + collection creation run synchronously (needed immediately by document routes); loading the embedding model and building the vectorstore/retriever/agent happens in a background thread (`init_resources` → `_load_resources`) so container startup doesn't block on a model download. Code needing `app.extensions["agent"]`/`"dense_embeddings"` must gate on `wait_for_resources(timeout=...)` first (see `app/api/documents.py:trigger_ingestion`).
- Package map of `app/` (one package per area; HTTP only in `app/api/`, which calls into the others):
  - `core/` infrastructure: SQLAlchemy models, `database_service`, `settings_service`, crypto, CSRF, security headers, version, device, phase logger, Qdrant client.
  - `auth/` users, roles, grants (`access`), audit log, LDAP/OIDC (`ldap.py`, `oidc.py`, shared `external.py`), user/group admin.
  - `llm/` connections, model registry, chat-LLM factory, vision LLM.
  - `ingest/` file -> Markdown -> chunks -> Qdrant: `loaders/` (Docling preprocessing, OCR), `splitter`, `indexer`, tables (`tables`, `table_merge`, `table_vision`), `pipeline.py` (`DocumentIngestion`), `reindex.py`.
  - `knowledge/` knowledge areas: `service.py` (CRUD, paths, kinds), `index_doc.py` (`index.md`), `files.py`, `external.py` (foreign Qdrant), `sql/` (SQL sources and value directory).
  - `rag/` retrieval: scope, profiles, pipeline, query enhancement, BM25 language, embedding/rerank registry and endpoints, collection setup.
  - `agent/` document agent, behavior prompt, context guard, `resources.py` (startup loading), `tools/` (model tools, web search) and `toolworker/` (client + settings).
  - `chat/` attachments, compaction, PII session and client, summaries (incl. DOCX export), my uploads, data export, STT.
  - `api/` blueprints: `pages` (no prefix: SPA, login, health), `chat` (`/chat`, sessions, attachments, STT), `auth` (login, OIDC, own account, version), `users`, `knowledge`, `documents` (documents, data files, vector DB, my uploads, ingestion status), `summaries`, `models` (connections, model configs), `admin` (`/api/admin/*`), `retrieval`; `tool_checks.py` holds the Admin › Tools connection tests, `_common.py` the few helpers shared by several blueprints. New blueprints go into `register_blueprints` (`app/api/__init__.py`); tests use the same function.
- Database service singleton: `app/core/database_service.py:init_db_service()` / `get_db_service()`. Every method opens its own session and closes it in `finally` before returning — see the DetachedInstanceError gotcha below.
- Models: `app/core/models.py`. Settings model is the source of truth for runtime config.
- Settings resolution order: `settings_service.py` reads DB first, then `.env`/environment, then default. A stale DB row silently wins over a correct env var indefinitely — check the `settings` table first when an env var "doesn't take effect".
- Qdrant client factory: `app/core/qdrant_client.py`. Connects to a running Qdrant server at `QDRANT_HOST:QDRANT_PORT` (default `localhost:6333`). No embedded/local file mode.
- Knowledge areas (`app/knowledge/service.py`, table `knowledge`): every area has its **own Qdrant collection** (`kb_<id>`). The seeded default area uses the collection `open_knowledge_ui` and the flat data folders. `knowledge_paths()` resolves the per-area folders; structured data of non-default areas lives in `DATA_DIR/knowledge_<id>/` and is addressed by Pandas tools as `knowledge_<id>/<file>`. API endpoints take `?knowledge_id=` (omitted = default area). Collections are created via `app/rag/collections.py:ensure_collection`. Embedding config is copied from the global settings at creation (informational for now; all areas share the global embedding instance).
- Retrieval scope: the agent/retriever are singletons. `app/rag/retrieval.py:MultiCollectionRetriever` reads the per-request `RetrievalScope` from a `ContextVar` that `/chat` sets inside the agent loop (`knowledge_ids` from the request body; `null` = all areas). Round-robin merge, no cross-collection scores. Without a scope it searches only `open_knowledge_ui`.
- Access control (`app/auth/access.py`, tables `groups`, `group_members`, `resource_grants`, flags `knowledge.is_public` / `model_configs.is_public`; user/group admin in `app/auth/user_admin.py` + `app/api/users.py`): a **model** is usable if the user is admin, it is public, or a grant exists; a **knowledge area** is accessible if it is public (read only) or a grant exists for the user or one of their groups (`write` implies `read`) - admins have **no** bypass for knowledge (deliberate: an admin must not see everything and attach it to models; the creator's automatic `write` grant is what gives access). Migration 0011 marks all pre-existing knowledge areas public (behavior unchanged); new knowledge starts private, the creator gets a `write` grant, new model clones start private (unconfigured base models are public). Rules to preserve: (1) every `knowledge_id` endpoint in `app/api/documents.py` goes through `_current_knowledge()` (read for GET, write otherwise) and is wrapped with `@knowledge_scoped`, which runs the check *before* the handler (inside a handler's `try/except Exception` the abort would turn into a 500); denials are 404 so IDs do not leak; (2) `/chat` intersects the requested `knowledge_ids` with `accessible_knowledge_ids(user)` and never trusts request collections, except knowledge attached to the chosen model, which anyone allowed to use that model may search (`can_use_model`); (3) non-admin `/api/models` is filtered by `can_use_model` and carries no config; (4) saving a knowledge share list never removes the saving user's own write access; (5) deleting a user/group/knowledge/model/connection removes its grants. Last active admin, own role/status and self-delete are protected. Users change their own password via `POST /api/auth/change-password`. OIDC is not implemented.
- Retrieval profiles (`app/rag/`: `profiles.py` validated config + CRUD, `pipeline.py` stages, `queries.py` LLM question generation, `helper.py` helper LLM, `format.py` source-labelled tool output, `routes.py` API; tables `retrieval_profiles`, `knowledge.retrieval_profile_id`): a profile is chosen **only on the knowledge** (NULL = default profile, switching takes effect immediately, no re-ingestion; there is deliberately no profile on models). Pipeline: optional LLM query expansion -> `query_points` per question and collection (dense + BM25 prefetch, weighted RRF or DBSF) -> RRF merge -> optional rerank against the *original* question -> optional MMR -> top `final_k` -> optional neighbor chunks (`chunk_index`/`chunk_total`, only for data ingested since 0.1.0). Every optional stage falls back instead of failing (trace records it). Seeds: "Standard" (hybrid + `BAAI/bge-reranker-base` + neighbors=1, no extra LLM call), "Gründlich" (+ multi-query), "Schnell" (old behavior from `RETRIEVER_*`). Defaults were chosen by measurement on a German test corpus (13 questions, hit@1: hybrid 10, +bge-reranker-base 12, +jina-v2-multilingual 11, +multi-query no gain), so do not change them without re-measuring; the multilingual Jina model was *worse* than the English MiniLM on a small German check. Users should never have to pick a strategy: the choice is under "Erweitert" on the knowledge page. The global reranker preloads at startup (`model_settings.prepare`). Admin test endpoint `POST /api/retrieval/test` returns the stage trace.
- Qdrant collections (`app/rag/collections.py:ensure_collection`, the only place that creates them): dense vector with **HNSW** (`m=16, ef_construct=100`) and the BM25 sparse vector `langchain-sparse` with **`modifier=IDF`** (fastembed BM25 queries are all 1.0, IDF must come from the server; without it keyword search is much weaker). Existing collections without the modifier are upgraded at startup. Ingestion always writes both vectors; never drop either.
- LLM connections and models (`app/llm/connections.py`, `app/llm/registry.py`, `app/llm/factory.py`, `app/api/models.py`; tables `connections`, `model_configs`): OpenAI-compatible endpoints (LiteLLM, vLLM, Ollama, OpenAI; Claude via LiteLLM) with base URL + API key (plaintext in SQLite like the other keys; never returned by the API; blank key on edit = keep, but only while the base URL is unchanged, and the stored key is only ever sent to the stored URL; link-local targets like 169.254.x.x are rejected, private LAN addresses are allowed). Models are fetched live from `<base_url>/models` (60 s cache). A model is addressed by ref `base:<connection_id>:<model_id>` or `clone:<config_id>`. `model_configs` holds per-model overrides (prompt appended after the fixed base prompt and the global default instructions, see below; there is no "replace base prompt" any more (migration 0030 dropped `replace_prompt`), sampling params over the global `CHAT_*` defaults, attached knowledge ids) and clones. `/chat` takes `model`; `registry.get_agent` builds a fresh `DocumentAgent` (and LLM client) per chat request and deliberately does not cache it: every request runs in its own event loop that is closed afterwards, and a cached `ChatOpenAI` keeps an async HTTP pool whose keep-alive connections are bound to a dead loop (`RuntimeError: Event loop is closed` on the following request). Config edits therefore take effect immediately. A model with attached knowledge always searches exactly those areas and ignores the request's `knowledge_ids`. `DEFAULT_MODEL` (hidden from the settings UI) is the default; without it the legacy `CHAT_MODEL` on the first active connection is used. The seeded "Standard" connection comes from `CHAT_BASEURL`/`API_KEY` (`ensure_default_connection`, at runtime because fresh DBs have no settings rows during migrations). Vision/ingestion LLMs still use `VISION_*` and are not selected via connections.
- **PII filter limits** (`app/chat/pii_session.py`, settings `PII_FILTER_TIMEOUT_S` default 10 and `PII_FILTER_MAX_CHARS` default 12000, migration 0035, client built in `app/agent/tools/web_access.py:pii_client`): the timeout is `timeout_for(len, client.timeout)` (base + 1 s per 2000 chars, max 60) for conversation AND tool texts (`mask_or_fail`); `PIIFilterClient.filter_text` retries once on timeout/connection error/5xx with double the limit (4xx final); texts longer than `max_chars` go in pieces (`split_text`, `mask_conversation` batches, `PIISession.mask_tool_text` loops) merged with `merge_masked`. Measured on a real EntityGuard: 8-12k chars 1.6-2.8 s warm but 17-34 s cold/under load, 50k chars crashed the service. User-facing wording comes only from `unavailable_message(reason)` (never addresses). Plain years are not masked (`keep_years`), SQL tools mask only data values (`PIISession.mask_values`).
- **Tool history**: the generator keeps `tool_calls` (name, masked input, masked output) and appends `tools_block()` = `<tools>[json]</tools>` before `<sources>` to the saved assistant message (max 20 calls, 2000 chars each, `</` escaped); `compaction.clean_history_text` strips it for the model, `Message.tsx:splitTools` shows it. Live `tool_result` events carry the unmasked output/input (display only); never store those.
- **Secrets at rest** (`app/core/crypto.py`): Fernet, values stored as `enc:v1:<token>`. `EncryptedText` (SQLAlchemy `TypeDecorator`) is the column type of `connections.api_key` and `knowledge.source_config`; sensitive settings (`SettingsService.encrypted_keys()` = `SENSITIVE_KEYS` minus `APP_PASSWORD_HASH`, a hash) are encrypted in `SettingsService.get/set/seed` including `default_value` (always go through `SettingsService`, never read `Setting.value` raw for those). Key: env `ENCRYPTION_KEY` (comma list = rotation, first encrypts) or auto-created `<DATA_DIR>/.encryption_key` (0600, warns). `crypto.encrypt_existing` runs at the end of `init_default_data`: encrypts legacy plaintext (idempotent) and raises `SecretKeyError` when an encrypted value does not open - startup must fail, never continue with empty credentials. Documents/chats/vectors are NOT encrypted. Tests get a random key per test (`fixed_encryption_key` in `tests/conftest.py`).
- **CSRF** (`app/core/csrf.py`, installed in `create_app`, tests of other modules build bare Flask apps without it): session token `session["csrf_token"]` mirrored in the readable cookie `csrf_token`; every POST/PUT/PATCH/DELETE needs header `X-CSRF-Token` (or form field `csrf_token`), compared with `hmac.compare_digest`, else 403 JSON. `frontend/src/lib/api.ts:csrfHeaders()` adds it (also used by the raw `fetch("/chat")`); a new raw `fetch` with a changing method must add it too. `session.clear()` (login/logout) rotates it. Session cookie `HttpOnly` + `SameSite=Lax` (+ `Secure` via `SESSION_COOKIE_SECURE`); `/ws/stt-stream` checks `Origin` against the host (`csrf.same_origin`). `app.config["CSRF_ENABLED"] = False` switches the check off.
- **BM25 language** (`app/rag/sparse.py`, setting `BM25_LANGUAGE`, default `german`, `knowledge.bm25_language`, migration 0034): `app.extensions["sparse_embeddings"]` is a `SparseRouter` (same `embed_documents/embed_query` interface as `FastEmbedSparse` using the default language, plus `for_language(lang)`). The stemmer/stopword language is baked into the sparse vectors, so documents and queries must use the same one: ingestion encodes with the knowledge's language (`DocumentIngestion._sparse_for_index`; chat attachments use the current default), `RetrievalScope.sparse_langs` makes `MultiCollectionRetriever` group collections by language, NULL = legacy = English, `model_settings.is_stale` flags knowledge whose language differs from the setting, reindex stamps the current language (`swap_collection`). External sources stay English (`LEGACY_LANGUAGE`). Use `sparse.resolve(sparse, lang)` where an encoder is passed on (test fakes without `for_language` pass through). Measured on 118 generated German paragraphs (BM25 only): hit@1 39 -> 48, MRR 0.425 -> 0.499; German without the stemmer was worse than English (36).
- Chat attachments (`app/chat/attachments.py`): uploaded via `POST /api/chat/attachments`, ingested in a background thread (fixed ingestion: no LLM context enrichment, no archive move) into collection `user_uploads` with `session_id` in the payload; search filters on it. Deleting a session removes them. Document types (PDF/DOCX/DOC/ODT/MD) and images (`IMAGE_EXTS`: png/jpg/jpeg/webp/gif/bmp), no CSV/Excel. **Images**: ingest task `images` (`app/ingest/tasks.py`, setting `INGEST_CHAT_IMAGES`, `IMAGES_PROMPT`/`IMAGES_MODEL_REF`/..., empty model = the vision task's model, migration 0032): `app/ingest/image_text.py:image_to_markdown` lets the vision model read the picture once (`encode_image`: EXIF rotation, transparency to white, max 2048 px) and `DocumentIngestion._load_markdown` returns that Markdown, so it is split/embedded/searched/PII-masked like any attachment; a failure reaches the user through `ingest.errors` as the attachment error. At upload a shrunk copy `bild.jpg` is kept in the attachment folder (`attachments.image_copy_path/image_data_url`). **Direct image path**: `model_configs.vision` ("Versteht Bilder", migration 0033, default off, `ResolvedModel.vision`, in `/api/models` for everyone): `/chat` takes `attachment_ids` (only the user's own images of this session) and, if the model has `vision`, turns the LAST message into `[text, image_url...]` right before `input_data` (after PII masking and compaction, which only ever see text). The frontend then does not wait for the text reading of image attachments. The PII filter cannot mask images: both the vision task's model and a `vision` chat model see the raw picture, so the admin's model choice is the protection (warning on the switch). Measured: reading 25/25 texts on 4 images; direct vs text-only path no difference on 6 chart/colour/checkbox questions (+~300 prompt tokens per image).
- Vector collection of the default area is `"open_knowledge_ui"` and uses hybrid retrieval (`langchain_qdrant` dense + FastEmbedSparse BM25). One Qdrant point per chunk; all chunks of one ingested file share a `file_group_id` payload value, which file-level list/delete operations filter on (a file is never one point).
- Embedding dimension is never typed in: it is probed from the model (`models_runtime.get_embedder(spec).dimension`) and stored per knowledge (`knowledge.embedding_dimension`). `EMBEDDING_DIMENSION` is a dead legacy setting.
- Shared knowledge base, not per-user silos: any document uploaded by anyone is retrievable by everyone in chat (intentional). `UserDocument`/`UserSummaryFile` rows are ownership bookkeeping for the "my documents"/"my analyses" management UI, not an access-control boundary — retrieval is never filtered by uploader.
- `app/agent/tools/custom_tools.py:CustomTools` is instantiated **once** at app startup and shared across every request — it has no per-request state. Summary tracking (`_track_summary_for_current_user`) calls `get_db_service()` directly (single-user, no Flask session inspection needed).
- Linux/Docker runs `gunicorn -w 1 --threads 4 -k gthread` (`run_linux.py`). Worker count must stay at 1 — several module-level globals are process-wide, not per-worker-safe (`app/__init__.py`'s `_qdrant_client`/`_db_service`, the shared ingestion status in `app.extensions["ingestion_status"]`). Threads exist so a long-lived SSE chat stream doesn't block every other request app-wide.
- Tailwind is **v4** compiled by the Vite plugin (`@tailwindcss/vite`) at `npm run build` time — there is no standalone CLI, no `tailwind.config.js`, and no live watch. Utilities are generated from `frontend/src/**` sources. The design tokens (ChatGPT-like neutrals) live in `frontend/src/index.css` under `@theme inline` (`--color-surface`/`--color-primary`/`--color-border-base` …) mapping raw `--rag-*` CSS vars; `.dark` overrides them (class-based dark mode). **Do not** add per-element `dark:` variants — extend the tokens instead. New utility classes only take effect after a rebuild (`cd frontend && npm run build`) or via `npm run dev` (Vite HMR).
- **Models are a registry** (`app/rag/models_runtime.py`): `ModelSpec{source: hf|endpoint|fastembed, model, connection_id}` -> cached embedder/reranker (`hf` = sentence-transformers `SentenceTransformer`/`CrossEncoder`, `endpoint` = OpenAI `/embeddings` and `POST /rerank` of a Connection incl. link-local block, `fastembed` = legacy only). Global specs live in settings `EMBEDDING_SPEC`/`RERANKER_SPEC` (`app/rag/model_settings.py`; fresh install = HF MiniLM + `bge-reranker-base`, upgraded installs = same models via fastembed, migration `0014`). Loading is lazy and in the background at startup/after saving (`status()` for the UI, failures cached 60 s). **Never embed without a spec**: each knowledge stores `embedding_spec` + `index_signature` (hash of model, chunk settings, `SPLITTER_VERSION`, `PARSER_VERSION`); queries (`RetrievalScope.specs`) and new ingestion use *the knowledge's* model, not the global one, so search stays correct until it is re-indexed. `model_settings.is_stale()` drives the "Index veraltet" banner. Chat attachments always use the current global model in `user_uploads_<hash>`. Admin UI: tab "Einlesen & Modelle" in the Administration modal (`AdminDialog`, all admin areas live there, no `/admin/*` routes), API `/api/admin/embedding*`. The profile's `rerank.model` is always `"default"` (global reranker).
- Document parsing uses **Docling** for PDF, DOCX/DOC/ODT; the wrappers return **Markdown** (`PreprocessBase.build_markdown_from_docling`: tables as Markdown or CSV reference blocks via `app/ingest/tables.py`, images as `[BILD-BESCHREIBUNG: ...]` through VisionLLM with phash dedup). `app/ingest/splitter.py` (`split_markdown`, `SPLITTER_VERSION`) splits by headers `#`-`####` (oversized sections recursively, small ones merged, table rows with repeated header; heading path prepended to the embedded text) and `app/ingest/indexer.py` (`build_points`, `PARSER_VERSION`) builds the Qdrant points. The Markdown is stored at `data/markdown/<knowledge_id>/<file_group_id>.md` (`UserDocument.markdown_path`), is viewable via `GET /api/documents/<id>/markdown` and is the source for re-indexing. Bump `SPLITTER_VERSION`/`PARSER_VERSION` when changing splitting/parsing so indexes become stale. `.md` uses LangChain `TextLoader`. `unstructured` and `python-docx` are fully removed.
- **Re-indexing** (`app/ingest/reindex.py`): background job, blue/green (`<collection>_g<n>` built next to the old one, swapped in one DB transaction via `knowledge.swap_collection`, old dropped, failure keeps the old one and sets `last_reindex_error`). Docs without stored Markdown are re-parsed from `processed_files`, else rebuilt from old chunks. While running, mutating calls on that knowledge return 409 (`_abort_if_reindexing`). The default knowledge's collection may be renamed (`open_knowledge_ui_g1`): look it up by `is_default`, never by the literal `open_knowledge_ui`. Endpoints `POST /api/knowledge/<id>/reindex`, `POST /api/reindex-all`, `GET /api/reindex/status`.
- **Table of contents per knowledge** (`app/knowledge/index_doc.py`; stored on the knowledge row as `index_md`/`index_updated_at`, migration 0029, not as a file — so a chat can only read the index of the knowledge in its scope; `refresh_index` rebuilds, `ensure_index` creates it lazily, legacy `index.md` files are deleted on rebuild): auto-built table of contents the agent reads first (`read_knowledge_index` tool; small ones appended to the question). Kept because an A/B run (16 runs each) showed 16/16 vs 15/16 correct, 1.1 vs 2.2 tool calls, 22 vs 25 s. Switch `INGEST_INDEX_ENABLED`.
- The pandas tools only see the data folders of the knowledge selected in the chat (`RetrievalScope.data_dirs`, `CustomTools._allowed_files`); never widen that to the whole `DATA_DIR`.
- `langchain-huggingface` is **not** a dependency. Dense embeddings/rerankers come from the registry above; only the BM25 sparse model (`FastEmbedSparse("Qdrant/bm25")`) is fixed. `torch` **is** a direct dependency (CPU-only, pinned via `[tool.uv.sources]` to the PyTorch CPU wheel index) — needed by Docling and `sentence-transformers`, but listed explicitly so uv's source mapping applies (a purely transitive requirement ignores `[tool.uv.sources]`; see the inline comment in `pyproject.toml`). `pyproject.toml` pins the CPU wheel for local dev; the Docker image swaps in CUDA torch (`ARG TORCH_BACKEND`, default `cuda`) and compose reserves the GPU. Note `uv sync`/`uv run` reverts a CUDA-torch venv to the CPU wheel. Device choice lives in `app/core/device.py` (`torch_device()`: cuda > mps > cpu, override `RAG_DEVICE`; `onnx_providers()` adds CoreML on macOS); `run_mac.py` is the macOS launcher: only the app runs natively (MPS needs the host), helper services stay in Docker via `docker-compose.mac.yml`. large models are slow on CPU.
- `gradio` and `sentence-transformers` are direct deps in `pyproject.toml` with **zero imports** in `app/`/`scripts/`/`parakeet/` (as of this writing). `sentence-transformers` is pulled transitively by other libs but unused directly; `gradio` appears unused entirely. Don't remove either blindly without checking `uv tree` — `sentence-transformers` may still be a transitive provider something resolves to.

## Document ingestion

Dokumente werden **über das Web-Interface** eingelesen. Es ist kein separates CLI-Skript mehr nötig.

- Dokumente-Bereich (`/api/documents`) und Vektordatenbank-Bereich (`/api/vectordb`): Dateien hochladen → **Ingestion starten**. Ingestion läuft synchron (`app.ingest.pipeline.DocumentIngestion.ingest_documents()`, aufgerufen aus `app/api/documents.py:trigger_ingestion`) — der Request blockiert bis Ingestion fertig ist, kein Hintergrund-Job/Queue.
- **Prompt in three layers** (`DocumentAgent.compose_prompt`): (1) `DocumentAgent.SYSTEM_PROMPT` in code = only tool list and rules that keep tool calls and the source display safe (`[n]` citations, answers only from tool results, `run_pandas` for reference chunks, the table of contents is for orientation and never recited); (2) default instructions in the DB (`AGENT_BEHAVIOR_PROMPT`, `app/agent/behavior.py`, seeded by migration 0030, edited on the Models page via `/api/admin/agent-behavior`, an empty text is allowed): role, language, style, summaries, overview questions; (3) the per-model prompt (brand voice). Rolle/Sprache/Stil never go back into the base prompt. The agent cache key includes the composed prompt, so edits apply at once.
- **Strukturierte Daten (CSV/XLSX/XLS) werden NICHT als Inhalt in die Vektordatenbank ingestet.** Sie sind reine Pandas-Referenz: Der Upload (`store_uploaded_files` in `app/knowledge/files.py`) legt sie sofort in `DATA_DIR` ab (Kollisionsschutz per Timestamp-Suffix) und listet sie über `/api/data-files`; genutzt werden sie ausschließlich über die Tools `list_files`/`preview_data`/`run_pandas`. **Pro Datei wird jedoch ein schlanker Verweis-Chunk** (`type='data_reference'`, `file_group_id=filename`) über `app.ingest.pipeline.index_data_references()` in Qdrant geschrieben — mit Dateiname, Spalten, Zeilenzahl und dem Hinweis, dass Details per `run_pandas` zu holen sind (Text beginnt mit `[STRUKTURIERTE DATEN]`). So findet das Modell die Tabelle semantisch, ohne die Daten zu duplizieren. **Second pass for PDF tables** (`app/ingest/table_vision.py`, ingest task `tables` in `app/ingest/tasks.py`, setting `INGEST_TABLE_VISION`, prompt `TABLES_PROMPT`, model empty = the vision task's model, `TABLES_MAX_ROW_DEVIATION`, migration 0031): `PreprocessBase._extract_tables` renders each table's area with pypdfium2 (`PageRenderer`, one page in memory), sends image + Docling draft to the vision model and takes the answer only if `parse_markdown_table`/`is_plausible` accept it; otherwise the Docling frame stays. PDF only, only with a `table_sink` (not chat attachments) and only while image description is on. Measured on 8 generated PDFs: cell accuracy 0.63 → 0.99, table shape 5/8 → 8/8. **Tables across pages** (`app/ingest/table_merge.py`): `_extract_tables` first collects all tables (after the vision pass), then groups consecutive ones with `is_continuation` (next page, first ends in the bottom 15 % / second starts in the top 15 % of its page, nothing but tables in between in `iterate_items`, same column count and x-position, repeated header or a header row that looks like a data row of the first) and `merge_frames` (drops repeated headers, turns a data row misread as header back into a row). One CSV and one reference `[TABELLE n (Seiten a–b): …]` per group. **Tables extracted from PDF/DOCX (`<stem>--<id8>--tabelle-<n>.csv`, `app/ingest/tables.py:is_extracted_table`) get NO chunk of their own** — they belong to their document: the reference with columns and content hints (`column_hints_text`) is part of the document's markdown (`render_reference`), and `index_data_references` skips them and deletes old points of that kind. Der Verweis wird beim Upload (best-effort, nur wenn Embeddings geladen) und bei jedem „Ingestion starten" idempotent neu geschrieben; beim Löschen entfernt `delete_data_reference()` ihn. Nur Dokumente (PDF/DOCX/DOC/ODT/MD) landen in `data/files/` und werden als Volltext ingestet; nach Erfolg wandern sie nach `data/processed_files/`.
- Unter Windows wird Qdrant als `qdrant.exe` von `run_windows.py` gestartet (Server-Modus auf `127.0.0.1:6333`), sodass Flask und Ingestion gleichzeitig laufen können.

## Common gotchas

- **DB sessions:** `DatabaseService.get_session()` auto-closes sessions opened inside a request (`after_this_request`), but background threads must close their own. Never keep a long-lived session (`app.extensions["settings"]` is a `LiveSettingsService` that opens a short session per call) — a cached session returns stale settings and, on Postgres, holds a connection from the pool.
- **Postgres vs SQLite in migrations:** no `INSERT OR IGNORE`, no integer literals for booleans, no `lastrowid` (use `RETURNING`). Test migrations against a real Postgres (`TEST_DATABASE_URL=postgresql+psycopg://... pytest`; the suite recreates the schema per test).
- **Settings drift:** Admin panel edits live in the `settings` table and win over `.env`/environment variables silently and indefinitely — a stale DB row can override a correct env var forever. Check the `settings` table before trusting `.env` when something "doesn't take effect" (bit us with `QDRANT_HOST` stuck at `localhost` from an old run). `env.example` contains only Qdrant infra vars, the OCR trio (`OCR_ENGINE`/`OCR_LANGUAGES`/`OCR_TESSERACT_CMD`) and the Postgres/crypto/worker bootstrap — all app config (LLM, embedding, retriever, storage, API keys, STT) lives in the `settings` table.
- **API_KEY no longer needs `.env`:** `API_KEY` is read from the settings DB (like all other config), with `os.getenv` only as standalone fallback. The `docker-compose.yml` no longer passes `API_KEY` as an environment variable. The settings DB row is seeded with default `'ollama'` on first migration.
- **Embedding dimension mismatch** makes Qdrant drop or reject points (the in-memory test client drops them silently): test fakes must expose `dimension` matching the collection. Model config lives in the `settings` table and the admin page, not in `env.example`.
- **Embedding backend change requires re-ingestion:** switching from Torch (`HuggingFaceEmbeddings`) to ONNX (`FastEmbedEmbeddings`) changes vector values for the "same" model — old and new vectors coexist in the collection with slightly different geometries. Re-ingest all documents after swapping backends.
- **OCR engine is env-only** (`app/ingest/loaders/ocr.py`, setting `OCR_ENGINE` default `tesseract`; also `OCR_LANGUAGES` default `deu,eng`, `OCR_TESSERACT_CMD` optional binary path; all in `ENV_ONLY_KEYS`, read via `os.getenv` like `QDRANT_*`): applied in `preprocess_pdf.py:_build_converter`. Fallback rules: unknown value / missing package / `ocrmac` on non-mac → warning + Tesseract CLI; `off` builds the pipeline with `do_ocr=False`. `docling-slim[standard]` already ships `rapidocr` + `onnxruntime` — no new dependency; language codes differ per engine (tesseract `deu`, rapidocr `de` first-wins, ocrmac `de-DE`). The old `TESSERACT_CMD`/`TESSERACT_PATH`/`POPPLER_PATH` variables in `env.example` are dead — replaced by the OCR trio. Use `TesseractCliOcrOptions`, **never** `TesseractOcrOptions` (the latter needs the `tesserocr` Cython binding + `libtesseract-dev`/`libleptonica-dev` build headers — painful and unnecessary).
- **Qdrant must be running** before starting the app (server mode only; no embedded file fallback). On Windows, `run_windows.py` auto-starts `qdrant.exe`; on Linux, use Docker Compose or run Qdrant separately.
- **Qdrant server migration:** `scripts/manage_qdrant.py` (`uv run python scripts/manage_qdrant.py status|migrate|info`) can move a collection between two Qdrant server instances.
- **DetachedInstanceError risk:** `DatabaseService` methods close their session before returning ORM objects. Any relationship on a returned object (e.g. `ChatSession.messages`, `Message.session`) not eager-loaded (`joinedload`) raises `DetachedInstanceError` the moment it's accessed later — already happened once with `get_summary_by_filename` (a relationship access). Plain columns are always safe; relationships are not unless eager-loaded.
- **"Tracking" DB writes are easy to forget to wire up:** `add_document()`/`create_summary_file()` existed with zero callers for a while — files were written/ingested correctly but silently never appeared in the "my documents"/"my analyses" UI because nothing called the DB-row-creating method. When adding a "create X and track it" flow, grep for actual callers, don't assume it's wired in just because the method exists.
- **Gunicorn worker count:** stay at `-w 1` (see architecture facts above) — multiple worker processes would each get their own copy of the module-level globals several routes depend on.
- **fastembed mean-pooling change:** fastembed ≥0.6 switched `paraphrase-multilingual-MiniLM-L12-v2` from CLS-token to mean pooling. Vectors embedded with fastembed ≤0.5.1 (CLS) are NOT compatible with new embeddings — re-ingest all documents after upgrading fastembed. The `UserWarning` about this is intentionally suppressed in `app/__init__.py` (the new behaviour is correct); don't remove that filter without a reason.
- **torch CPU pin (uv):** `torch`/`torchvision` must stay direct deps in `pyproject.toml` (not just transitive) for `[tool.uv.sources]` to route them to the `pytorch-cpu` wheel index — a purely transitive requirement ignores source mapping and would pull the multi-GB CUDA wheel instead. The `explicit = true` on `[[tool.uv.index]]` scopes the index to only the mapped packages, so all other deps still resolve from PyPI. Don't "clean up" torch/torchvision out of `dependencies` without checking this.
- **Pillow 13 only via override:** `fastembed 0.9.0` declares `pillow<13` (for Python >=3.14 even `>=12,<13`), although PIL is only imported by its image/multimodal modules — not by the BM25 sparse encoder or the cross-encoder used here. Pillow 13 fixes 39 CVEs, so `[tool.uv] override-dependencies` forces `pillow>=13.0.0,<14.0.0`. The upper bound mirrors docling and prevents a silent major upgrade, because an override replaces *all* requirements on that package. The Docker build uses the pip interface, which ignores `[tool.uv]`, and passes `uv-overrides.txt` via `--override` instead — keep both in sync and remove them once fastembed allows `pillow<14`. `gradio` (which also capped `pillow<13`) was dropped because the repo never imported it.
- **SearXNG JSON API needs explicit opt-in:** `docker-compose.yml`'s `searxng` service is configured via the checked-in `searxng/settings.yml`. By default SearXNG only serves HTML and its bot-protection limiter blocks non-browser requests — both `search.formats: [html, json]` and `server.limiter: false` are required there, otherwise `web_search_tool.py`'s `format=json` requests come back empty/403. `server.secret_key` must NOT be left as `ultrasecretkey` — newer SearXNG images hard-refuse to start with that literal value instead of auto-generating a replacement (older versions did); the checked-in file has a pre-generated random hex value, regenerate your own with `openssl rand -hex 32` for real deployments. `SEARCH_SEARXNG_URL` defaults to `http://searxng:8080` on a fresh DB (migration `0004`).
- **entityguard PII-filter service:** `docker-compose.yml`'s `entityguard` service (`registry.nutsolution.de/entityguard:latest`, port `9500`, no host port mapped) is the PII-filter backend for `app/chat/pii_client.py`. Its `/api/v1/sanitize` endpoint returns `mapping` as a **flat dict** `{"[NAME_1]": "Max Mustermann", ...}`, not a list of `{"placeholder":..., "original":...}` objects — `PIIFilterClient.demask()` handles both shapes (dict branch added after finding the mismatch would otherwise `AttributeError` on the first real call). `PII_FILTER_URL` defaults to `http://entityguard:9500/api/v1/sanitize` on a fresh DB (migration `0004`). `PII_FILTER_API_KEY` is sent as `Authorization: Bearer <key>` (not in the JSON body).
- **parakeet STT service needs a GPU (or explicit CPU build):** `docker-compose.yml`'s `parakeet` service (built from `parakeet/Dockerfile`, multi-stage `ARG DEVICE=gpu|cpu` selecting `nvidia/cuda:12.4.1-cudnn-runtime-ubuntu22.04` vs `python:3.12-slim`) requires the NVIDIA Container Toolkit on the host for the GPU build — the `deploy.resources.reservations.devices` GPU reservation block works with plain `docker compose up` (no Swarm needed) as of Compose v2, but the container won't start without a real GPU + toolkit unless built with `--build-arg DEVICE=cpu`. The Dockerfile has a benign internal quirk: `ARG DEVICE=gpu` (before the first `FROM`, used to pick the base image) and a *separately re-declared* `ARG DEVICE=cpu` (inside the final stage, used only for an otherwise-unused `ENV DEVICE=${DEVICE}`) have different defaults — harmless as long as `docker-compose.yml` always passes `args: {DEVICE: gpu}` explicitly (which it does), since a single `--build-arg`/`args:` value overrides every `ARG` declaration of that name throughout the build. Models are preloaded at build time (Parakeet ASR into the default HF cache, Silero VAD into a flat `/app/models/silero-vad` dir — `onnxruntime` rejects the HF cache's symlink-into-`blobs/` layout for the raw VAD session driven directly in `streaming.py`). `STT_BASEURL`/`STT_MODEL` default to `http://parakeet:5001/v1`/`nemo-parakeet-tdt-0.6b-v3` on a fresh DB. **The actual seed source is `alembic/versions/0002_single_user_conversion.py`** (`ON CONFLICT(key) DO NOTHING` insert), not `app/core/database_service.py:_init_settings()` — that Python dict has its own STT entries too, but they're dead code for a fresh install: migration 0002 always runs first (`run_linux.py`/`run_windows.py` both run `alembic upgrade head` before starting the server) and already inserts the row, so `_init_settings()`'s "insert if not exists" check finds it present and skips it. Keep both in sync if changing STT defaults again — easy to edit only one and have it silently not take effect (this bit us once: editing `database_service.py` alone left fresh installs still pointing at the old `whisper` URL). The batch `/api/stt` route (`app/api/chat.py`) still works against this same URL and is kept as a server-side fallback, but the chat UI's mic button no longer calls it.
- **Live STT streaming needs `flask-sock` + a background relay thread:** `app/chat/stt_stream.py` exposes `/ws/stt-stream`, a WebSocket endpoint (via `flask-sock`/`simple-websocket`, WSGI-socket-hijacking) that proxies raw float32 PCM from the browser to Parakeet's own `/v1/audio/stream` WebSocket (a plain synchronous `websocket-client` connection opened per browser session) and relays `partial`/`committed`/`final`/`error` JSON messages back. This only works under `gunicorn -k gthread` (the Linux/Docker path, `run_linux.py`) — **not** under `waitress` (`run_windows.py`), which has no socket-hijacking support, so live streaming STT is Docker-only; Windows users only get the batch `/api/stt` fallback. Each open recording occupies one of the app's 4 gunicorn threads for its whole duration (shares the pool with SSE chat streams) — fine for the single-user design, but don't lower `--threads` without checking this.
- **`parakeet/streaming.py`'s `ParakeetStreamEngine` must reuse `main.py`'s already-loaded ASR model, not load its own:** loading the ~0.6B-param Parakeet model a second time (one copy for the batch endpoint via `main.py`'s `get_model()`, a separate copy for the streaming engine) doubles GPU memory usage for the exact same weights — this OOM'd on a shared/modest GPU during verification (a 16MB Silero-VAD allocation failed only because the second ASR copy had already exhausted VRAM). Fixed by passing `asr_model=get_model()` into `parakeet_stream_engine.ensure_loaded()` in `main.py`'s lifespan handler; `ensure_loaded()`/`_load()` skip the redundant `onnx_asr.load_model()` call when given one. Also: the raw Silero VAD `onnxruntime.InferenceSession` in `streaming.py` is forced to `CPUExecutionProvider` regardless of the ASR provider — it's tiny (~2MB) and this avoids contending with the ASR model for GPU memory entirely.


## Models, vision and web search (current wiring)

- All chat/vision LLMs come from Connections (`app/llm/registry.py`); the legacy `CHAT_*`/`VISION_*`/`API_KEY` settings are hidden and unused for routing (sampling defaults in `app/llm/factory.py` still read `CHAT_*` as fallbacks). `VisionLLM` (`app/llm/local_llm.py`) resolves `VISION_MODEL_REF` (else the default model) on every call; it serves image descriptions and context enrichment. There is no startup "default agent" any more: `/chat` needs a resolvable model.
- Web search is a per-model tool (`ModelConfig.web_search`, migration 0015, default off). `app/agent/tools/web_access.py` builds it from live settings and only if `SEARCH_SEARXNG_URL` and an enabled `PII_FILTER_URL` exist; the config API rejects enabling it otherwise (400), and `/chat` appends the tool per request (agent cache key includes tool names). The PII client is built per use, not at startup.
- Infrastructure settings (`DATA_DIR`, `SUMMARIES_DIR`, `QDRANT_*`, `OCR_*`) are env-only (`SettingsService.ENV_ONLY_KEYS`): the DB value is ignored, so docker-compose env wins over stale seeded values.
- Ingestion never fails silently: `DocumentIngestion.errors/warnings/processed` are returned by `POST /api/documents/ingest` and shown as toasts; a failed file stays in the input folder and its extracted table CSVs are deleted.

Tests use the form values (`_FormSettings`) and only reuse the stored key for the stored URL.

## Chunk metadata (Qdrant payload)

- Per document chunk (`app/ingest/indexer.py:build_points` + `document_metadata`): `page_content` (embedded), `original_content`, `filename`, `source`, `title`, `headers` (list), `type`, `file_group_id`, `chunk_index`, `chunk_total`, `file_type`, `knowledge_id`, `uploaded_by`, `uploaded_at`, `parser_version`, `splitter_version`, plus `page_start`/`page_end` only when known. Attachments add `session_id`/`attachment_id`. Data-reference chunks (`type=data_reference`) exist only for uploaded CSV/Excel files and carry `file_type`, `knowledge_id`; tables extracted from documents have none (see above).
- Page numbers (PDF only): `PreprocessBase.build_markdown_from_docling` exports with a page-break placeholder and replaces it with `<!--p:N-->` markers (`apply_page_marks`; dropped if the break count does not match the page count). `split_markdown` strips the markers first and finds each chunk's words in the document to set `page_start/page_end` (`_assign_pages`; repeated table headers inherit the previous page). Markdown without markers means no pages. No `SPLITTER_VERSION` bump: new fields are optional, old data simply lacks them.
- No payload indexes for the new fields (no filtering yet); add them in `ensure_collection` before building filters.

## Ingest task prompts (DB-driven)

- Prompts, models and parameters of the two LLM ingest tasks live in `settings` (category `ingest`): `VISION_PROMPT`, `VISION_MODEL_REF`, `VISION_TEMPERATURE`, `VISION_MAX_TOKENS`, `INGEST_VISION_ENABLED`, and `CONTEXT_PROMPT` (placeholders `{dokument}`, `{abschnitt}`), `CONTEXT_EXCERPT_CHARS`, `CONTEXT_MODEL_REF`, `CONTEXT_TEMPERATURE`, `CONTEXT_MAX_TOKENS`, `INGEST_CONTEXT_ENRICHMENT`. `Setting.default_value` holds the standard prompt ("reset" reads it from there). Migration 0018 seeds them; `app/ingest/prompts.py` holds the seed texts only (fresh SQLite/test DBs and last-resort fallback) — never use them as runtime source.
- `app/ingest/tasks.py` (`load_task`, `render_context_prompt`, `validate_prompt`) reads the DB on every call; `TaskLLM(task)` (`app/llm/local_llm.py`, alias `VisionLLM`) resolves model and parameters per call. `DocumentIngestion.model` = vision, `.context_model` = context. Admin API: `tasks` in `/api/admin/embedding`.
- New LLM prompts or tunables belong in `settings` plus an Alembic migration, not in code.

## External sources (foreign vector stores, read-only)

- A foreign Qdrant is a Knowledge with `kind='external'` (migration 0019) and `source_config` JSON (`url`, `api_key`, `collection`, `dense_vector`, `sparse_vector`, `fields` mapping). Its collection_name is `ext_<id>` and is never created or deleted locally; the real collection is `source_config.collection`. `embedding_spec`/`embedding_dimension` hold the model **the admin declared** — nothing is auto-detected.
- `app/knowledge/external.py`: `parse_config`, `connect` (read client, `_reject_link_local`, timeout), `probe_source` (facts only), `validate_source` (hard checks: vector exists, dimension, text field, and a sample-point cosine check against the declared model, `MIN_SIMILARITY=0.8`), `normalize_payload`, `layout_for`. Retrieval: `RetrievalScope.externals` -> `MultiCollectionRetriever._run_external` -> `pipeline.run(layout=...)` (dense/sparse vector names, payload normalization, neighbors only with default `chunk_index`/`group` fields; without a sparse vector the search is dense-only). A down source never fails the chat: `scope.warnings` -> SSE `warning` event.
- Read-only everywhere: `_current_knowledge()` answers 409 for write requests and `/api/vectordb*` on external knowledge; reindex/stale/`ensure_collection`/index.md skip them; deleting only removes the row. Only admins create/change them; `source_config` is scrubbed to `{..., has_key}` in all API responses. Tests use a fake foreign server that refuses writes (`tests/test_external_sources.py`).
- Other store types (pgvector, OpenSearch, Chroma …) later: new `kind` values behind the same layout idea.

- Per-user/group filtering of external sources: `source_config.access` (`enabled`, `user_field`/`user_attr`, `group_field`/`groups_from`, `static`, `admins_unfiltered`). `sources.build_filter(cfg, identity)` returns `(qdrant Filter | None, blocked)`; `blocked` means the source returns nothing (fail closed). The filter is passed as `query_filter` to `pipeline.run` and re-applied to neighbor scrolls (`_expand_neighbors(..., extra_filter)`). Identity = `RetrievalScope.identity` (`username`, `display_name`, `groups` from `access.user_group_names`, `external_groups`, `is_admin`), filled in `app/api/chat.py`. Name matching is exact in Qdrant, so `_variants` sends common casings.

## Login with LDAP / OIDC (external accounts)

- Config lives in the DB (migration 0020): settings `AUTH_LDAP`, `AUTH_OIDC` (JSON, sensitive), `AUTH_DEFAULT_ROLE`, `AUTH_AUTO_CREATE`, `APP_BASE_URL`; user columns `auth_source` (`local|ldap|oidc`), `external_id`, `external_groups` (JSON, all group names the provider reported); `group_members.external` marks memberships set by a login. `app/auth/external.py` (config load/save with "empty secret = keep", `group_name_from`, `sync_groups`, `login_external_user`), `app/auth/ldap.py` (ldap3; `CLIENT_STRATEGY` is the test seam for `MOCK_SYNC`), `app/auth/oidc.py` (discovery cache, PKCE/state/nonce in the session, JWKS verification with PyJWT). API: `/api/auth/providers`, `/api/auth/oidc/login|callback`, `/api/admin/auth` (+`/test`).
- **Rule: groups are never imported.** `sync_groups` only matches provider group names (case-insensitive, DN -> CN) against **existing** local groups and never creates one; it only removes memberships with `external=True`. Roles never come from groups; new external accounts get `AUTH_DEFAULT_ROLE`.
- Local login always works and wins: a local account is only checked locally, an external login whose name collides with a local account is refused, external accounts have no password login/change (`users.authenticate`, `verify_password`, `set_password`). LDAP errors never block local login. Tests: `tests/test_external_auth.py` (ldap3 mock + a local fake OIDC provider with RSA-signed tokens).

## Markdown renderer (chat answers)

- `frontend/src/components/Markdown.tsx`: react-markdown with `remarkGfm` -> `rehypeSanitize` -> `rehypeHighlight`. **The order matters**: highlighting after the sanitizer, otherwise the `hljs-*` classes are stripped. Only `lowlight`'s `common` set plus `dockerfile` is registered, no language auto-detection. `pre` -> `chat/CodeBlock.tsx` (language, copy, wrap, fold >25 lines when not streaming, sticky header), `table` -> `chat/TableBlock.tsx` (scroll container, sticky head, copy as Markdown, CSV with BOM). Helpers in `lib/hastText.ts`. Colors/styles live in `index.css` (`.rag-code`, `.rag-table`), theme-aware.
- Streaming: `Markdown` is memoized and re-renders at most once per animation frame; `ChatPage.scrollToBottom(force)` only follows when the user is near the bottom. The look was borrowed as an idea from Open WebUI (license has a branding clause); no code was copied.
- Model dialog placeholders come from `GET /api/models` -> `param_defaults` (`llm/factory.global_chat_defaults`); there is no "global settings" page.

## Context compaction

- Budget (`app/chat/compaction.py:compute_budget`): usable = `num_ctx` - `max_tokens` (empty max_tokens -> `COMPACTION_OUTPUT_RESERVE_PERCENT` of the window), trigger = usable x (100 - `COMPACTION_HEADROOM_PERCENT`)%, keep = `COMPACTION_KEEP_PERCENT`% of usable stays verbatim. Usable < 1024 or `COMPACTION_ENABLED=false` -> no compaction. Settings and prompt (`COMPACTION_PROMPT`, placeholder `{messages}`, `default_value` for reset) live in the DB (migration 0021, seeded in `_init_settings`); API `/api/admin/compaction`; UI `CompactionCard.tsx` in the Tools tab; `ModelConfigDialog` shows budget/trigger from `GET /api/models` -> `compaction`.
- Level 1 (across requests, `app/api/chat.py` before the agent call): `db.get_history` returns the stored `sessions.summary` plus all messages after `summary_through_id`; `compaction.fit_history` summarizes older messages with the chat model when over the trigger, persists via `db.set_session_summary`, and emits SSE `compaction`. Original messages are never deleted. Failures are logged and the chat continues without compaction.
- Level 2 (inside the agent loop, `app/agent/context_guard.py`): `SummarizationMiddleware` (same trigger/keep, overhead of system prompt and tool schemas subtracted) plus `ToolResultClipMiddleware`. `registry.get_agent` reads budget and prompt on every request, so saving the settings takes effect immediately.
- Tokens are estimated offline (`CHARS_PER_TOKEN=3`, conservative); no tiktoken (downloads data). Display-only parts (`<think>`, `<sources>`) are stripped from the history (`clean_history_text`).

## Conversation-only chats and "Meine Ablagen"

- `app/api/chat.py` builds the scope first, then `select_tools(tools, has_knowledge)` (`app/agent/document_agent.py`): with no selected knowledge (`scope.collections/externals/data_dirs`) and no ready chat attachments the knowledge tools (`KNOWLEDGE_TOOLS`) are dropped and `CONVERSATION_ONLY_HINT` is appended to the user message (not the system prompt, to keep the agent cache). The agent is created *after* this (cache key includes the tool names). The system prompt has a "ZUSAMMENFASSUNG - erst die Quelle klären" rule: conversation summary = history only, document/knowledge summary = `document_search_tool`.
- "Meine Ablagen" is the UI name for the per-user markdown files (`/summaries`, `app/chat/summaries.py`, tools `list/read/write/edit_summary`); only display texts and tool descriptions were renamed, URLs, tables and tool names are unchanged. `write_summary` stores exactly what the user wants to file (conversation OR document analysis, never mixed).

## Speech input (stream vs upload)

- `app/chat/stt.py`: `STT_MODE` (`auto` default | `stream` | `upload`, DB setting, migration 0022), `resolve_mode` (auto probes `<base>/audio/stream` with a short WebSocket connect, cached 5 min per base URL), `transcribe` (OpenAI `audio.transcriptions`, link-local check, errors mapped to readable messages), `silent_wav` for the Tools test. `GET /api/stt/config` tells the browser `{available, mode}`; `POST /api/stt` (max 25 MB) is the upload path; `/ws/stt-stream` (`app/chat/stt_stream.py`) is the Parakeet-protocol relay and now forwards the API key as a Bearer header.
- Frontend `hooks/useStt.ts`: `mode=stream` = AudioWorklet PCM over WebSocket; `mode=upload` = `MediaRecorder` (webm/opus, mp4/ogg fallback), upload on stop, `transcribing` state shown as spinner in `Composer`. Both end in `onFinal(text)` (sends the message), the existing behavior.
- Tests: `tests/test_stt.py` (fake OpenAI endpoint, real WebSocket probe).

## PII filter (Sanitizer API) and web search

- Contract in `docs/sanitizer-api.md` (+ `sanitizer-openapi.yaml`, runnable adapter `docs/examples/sanitizer_adapter.py`): `POST {text}` -> `{filtered, mapping}`. `app/chat/pii_client.py:parse_response` (tolerant: `filtered|sanitized_text|result|text`, `mapping|entities|detected|pii_detected`; an *empty* filtered text is valid and never falls back to the original), `mapping_pairs`, `PIIFilterClient.demask`. `check_pii_filter` (`app/api/tool_checks.py`) verifies masking, mapping and demasking round-trip with invented data.
- Web search availability (`app/agent/tools/web_access.py`): SearXNG configured AND (active PII filter OR `SEARCH_ALLOW_UNMASKED`, default false, migration 0023). `web_search_masked()` drives the warnings in the model dialog. The tool (`web_search_tool.py`) is **fail-closed**: a configured filter that errors aborts the search; without mapping the filtered text is searched; a query that is only personal data is not sent. The chat path is **fail-closed** too and masks the WHOLE context in ONE call: `app/chat/pii_session.py:mask_conversation` joins summary + history + new question with `=====#i=====` markers, validates that the markers come back intact (else `PIIFilterUnavailable`), returns one mapping; `/chat` answers with an SSE `error` event (short reason via `short_reason`, never internal addresses) before anything reaches the model, nothing is saved. Compaction masks what it summarizes (`fit_history(mask_many=, unmask=)`) and stores the plain-text summary. `StreamDemasker` restores placeholders while streaming (tokens and reasoning; holds back possible placeholder prefixes). Known gaps: document hits (tool results) reach the model unmasked.


## Tool worker (isolated code execution)

- `run_pandas` no longer `exec()`s in the app. `tool_worker/` is its own Flask service (own `Dockerfile`, compose service `tool-worker`): `sandbox.check_code` (AST deny list: imports, dunder names/attrs/strings, `open`/`eval`/`exec`/`getattr`..., `read_*`/`to_*` I/O), one child process per call (`child.py`: `RLIMIT_AS/CPU/FSIZE`, `sys.addaudithook` denying file reads outside the Python tree, writes, sockets, subprocess), wall-clock kill, output cap. Namespace is `df`, `pd`, `np`, `result` only.
- The app decides which files are allowed (`CustomTools._allowed_files`, `RetrievalScope.data_dirs`) and sends only the path relative to `DATA_DIR`; the worker resolves it under its read-only `/data` mount and refuses anything outside (`..`, symlinks, other suffixes).
- App side: `app/agent/toolworker/` (`config.py` settings `TOOL_WORKER_URL`, `PANDAS_TIMEOUT_S`, `PANDAS_MAX_MEMORY_MB`, `PANDAS_MAX_OUTPUT_CHARS`, migration `0024`; `client.py` with injectable transport). The token (`TOOL_WORKER_TOKEN` / `_FILE`) is never stored in the DB. **No fallback** execution in the app: an unreachable worker yields `FEHLER: Codeausführung nicht verfügbar ...` and the chat continues.
- Tests use `tests/conftest.py::worker` (in-process Flask test client, root = the `CustomTools` data dir; depends on `db`). A test that calls `run_pandas` needs this fixture. Interface: `docs/tool-worker-api.md`.

## SQL knowledge (read-only live queries)

- `knowledge.kind='sql'` (`source_config` JSON, parsed by `app/knowledge/sql/config.py:SqlConfig`; the API only ever returns `public()` = `has_password`, and a stored password is only reused for the same dialect/host/instance/port/database/user). `app/knowledge/service.py:is_remote` (= external or sql) drives every "no local collection / read-only" branch; `is_sql` the SQL specifics. SQL knowledge has no collection, embeddings, files or table of contents; `/chat` splits it off before building the doc scope (`RetrievalScope.sql_sources` = `(id, name, config json)`).
- Execution is in the second worker service (`TOOL_WORKER_ROLE=sql`, `tool_worker/sqlengine.py`): read-only session per dialect, `tool_worker/sqlcheck.py` (sqlglot AST: one SELECT, deny functions, allowed tables, blocked columns incl. `*`/aliases), `LIMIT row_limit+1` + `fetchmany` to detect truncation, server-side timeout. MSSQL uses `pymssql` (no ODBC), named instances as `host\instance`; SQL Server has no read-only session, so the check + a SELECT-only user are the protection. The worker never sees app secrets; the SQL worker is the only service with egress.
- Tools `sql_schema`/`sql_query` (`app/knowledge/sql/tools.py`) read sources from the request scope; `select_tools(tools, has_knowledge, has_sql)` drops them without a SQL knowledge (and drops the document tools when only SQL is selected). Hint text comes from setting `SQL_PROMPT`.
- PII: `app/chat/pii_session.py:PIISession` (per request, `set_session` in the agent loop) unmasks tool arguments and masks tool results (fail-closed, `merge_masked` renames colliding placeholders); `StreamDemasker(session)` reads the pairs live. Without a configured filter nothing is masked or called.
- Tests: fixture `sql_worker` (in-process SQL worker, SQLite folder = `tmp_path/sqlite`); real servers via `SQL_TEST_PG`, `SQL_TEST_MYSQL`, `SQL_TEST_MSSQL` (`host:port:db:user:password`). Run the suite with `uv run --extra worker --with pytest pytest tests`.

## Connection kinds, model knowledge, roles

- `connections.kind` = `llm` (OpenAI-compatible, default) | `tei` | `infinity` (migration 0026). `app/rag/endpoints.py` is the only place that speaks the embedding/rerank wire formats (`embed`, `rerank`, `describe` = models + capabilities, `test_connection` = real API check); `models_runtime.EndpointEmbedder/EndpointReranker` delegate to it. TEI: `/embed` (`inputs`), `/rerank` (`texts`, scores come back sorted, map by `index`), `/info`; Infinity: `/embeddings`, `/rerank` (`documents`), `/models`. Addresses are tried with and without `/v1`. Non-`llm` connections are skipped by `registry.list_models`. Fake servers for tests: `tests/fake_inference.py`.
- Model knowledge (`model_configs.knowledge_ids`) is the **base** of every search; the request's `knowledge_ids` are added (limited to `accessible_knowledge_ids(user, "read")`) unless `model_configs.allow_extra_knowledge` is false (migration 0027, default true). A request without a selection searches only the model's knowledge. `/api/models` hands users `knowledge_base` (id, name) and `knowledge_locked` (= has knowledge and extras not allowed).
- Roles for knowledge: every endpoint that manages a knowledge is `require_role("user")` and checks the grant itself (`_current_knowledge` / `can_access_knowledge(..., "write")`); creators get a write grant. `access._granted` lets **editors** write on any knowledge granted to one of their groups (any level); role `user` keeps the granted level. Sharing (`/api/principals`, `/knowledge/<id>/access`) stays editor+, external/SQL sources admin.

## SQL value directory

- Problem: the model does not know the spellings in the source ("Stühle" vs `Stuhl`/`Bürostuhl`). Solution without copying data: `sql_values` (table, column, value, count; migration 0028) holds only the DISTINCT values of admin-chosen text columns (`source_config.value_columns`, kept by `_sql_source_from` when the dialog omits it), `sql_value_index` the build state. `app/knowledge/sql/valueindex.py`: `profile`/`suggest` (rules: skip sensitive names, > `SQL_VALUES_MAX_DISTINCT`, mostly unique), `start_build`/`build` (background thread, replaces rows only after a full successful read), `search`. Worker side: `/v1/sql/distinct`, `/v1/sql/profile` (`sqlengine.distinct_values`, `profile_columns`, both go through `validate_select`).
- Matching is purely lexical and was **measured** (see `app/knowledge/sql/values.py` docstring and `tests/test_sql_values_text.py`, which pins precision >= 0.95 / recall >= 0.98): exact key (casefold, ß=ss, ä=ae) 1.0 > same German stem 0.9 > stem is a substring of the value (compounds) 0.7 > trigram Dice >= 0.6. Dense embeddings were measured and rejected (precision 0.12 to 0.53). Do not add them without re-measuring.
- Tool `sql_find_values` (`SQL_TOOLS`), chat hint `SQL_VALUES_HINT` only when a source in the scope has values. Admin API under `/api/knowledge/<id>/sql-values*`, UI `SqlValuesCard.tsx`.

## Platforms and images

- Python: `.python-version` ist 3.14 (lokale Entwicklung), `requires-python = ">=3.12"` und das App-Image (`python:3.12-slim`) bleiben bei 3.12; der universale Lock deckt beides ab. Keine 3.14-only-Syntax in `app/` verwenden, Windows/macOS/Docker laufen weiterhin auf 3.12.
- `Dockerfile` defaults to `TORCH_BACKEND=cuda`; CPU/ARM needs `--build-arg TORCH_BACKEND=cpu` (the lock has aarch64 wheels, `uv pip compile --python-platform aarch64-unknown-linux-gnu --no-build` resolves). `docker-compose.cpu.yml` is the override (`!reset` of the GPU `deploy` blocks, `TORCH_BACKEND=cpu`, parakeet `DEVICE=cpu`).
- `.github/workflows/images.yml` (tag `vX.Y.Z`, or a manual run with inputs `version` (empty = `pyproject.toml` version, `dev` = trial) and `latest` (master only); a `meta` job decides version and whether `latest` is set): native runners per arch (no QEMU), push by digest, then `imagetools create` per image: app CUDA (amd64) `:X.Y.Z`/`:latest`, app CPU (amd64+arm64) `-cpu`, tool worker (amd64+arm64). `latest` is only set for release tags or an explicit master run, never for `dev`. Not run end to end locally (needs GitHub runners); linted with actionlint.
- macOS: `docker-compose.mac.yml` also runs `tool-worker` (port 8090) and `tool-worker-sql` (8091) on localhost because the app is native (no internal-only network possible with published ports). `run_mac.py` creates `TOOL_WORKER_TOKEN` in `.env` and rewrites the worker URLs in the settings, but only while they still hold the Docker default.
